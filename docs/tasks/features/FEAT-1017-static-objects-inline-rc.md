## 概要

生成コードの `dup` / `drop` は RC を読み、`rc > 0` (`dup`) と `rc > 1` (`drop`) を速い経路にして、残りを関数の末尾の冷たい
ブロックへ飛ばす。RC 0 の不死のオブジェクト (静的な空文字列・文字列定数・静的な構築子・IO トークン・FEAT-1012 の使わない葉) は、
MIR が静的と知っている値なら `dup` / `drop` ごと消える (FEAT-0089) が、引数やランタイムの結果として届くと冷たいブロックへ飛んで
戻る (`drop` は成立する分岐が 3 回)。

HTTP サーバの 1 要求で実行するコードのキャッシュラインは 100 本 (Rust 41 本) で、ユーザー空間の時間は命令数よりシステムコールの
後のキャッシュの外れで決まる (1 命令あたり約 4.3 ns)。Std.Net の `recvOn` が実行する 18 本のうち 7 本、`step` の 18 本のうち
約 7 本が、こうした冷たいブロックに 1〜4 命令だけ入る線である (`noTimeout`・空の残りのバッファ・空の受信結果)。

RC 0 を速い経路の前に調べ、静的なオブジェクトは同じ線の中で前へ飛ぶだけにする (速い経路は `dup` で 1 命令、`drop` で 2 命令
増える)。`drop` の冷たいブロックは `rc == 1` (解放) と `rc < 0` (共有) だけになる。

## メモ
- 2026-11-26: 前は FEAT-1012〜1015 の版、後は FEAT-1016 と合わせた版。HTTP サーバ (callgrind、20,000 要求): 1 要求の命令数は
  968 → 948、実行するコードのキャッシュラインは 98 → 92 本 (`recvOn` は `noTimeout`・空の受信結果の `drop` が冷たいブロックへ
  行かなくなり 8 → 5 本、`sendFrom` は 12 → 9 本)。スループット (200,000 要求、5 回の交互実行) の後/前の中央値は 16 接続で 1.000、
  64 接続で 1.003 で雑音の範囲、Rust/後は 1.015・1.014。全ベンチ (15 回の交互実行、binary-trees は 5 回。出力は同じ) の後/前の
  中央値: binary-trees 0.930 (葉の構築子は静的で、木の解放で葉の `drop` が速い経路になった。callgrind の命令数は深さ 16 で
  1,585M → 1,525M)、array-sort 0.987、session 0.989、spectral-norm 0.992、effects 0.998、cli-grep 0.999、binary-search・
  mandelbrot・n-body 1.000。string-split 1.014 と stencil 1.024 (最小値では 1.008) は、callgrind で実行する命令の数が関数ごとに
  前と同じ (熱いループは `dup` / `drop` を実行しない) で、差はコードの配置による: 前にある関数が短くなって熱い関数が 16〜48 バイト
  前へずれ、string-split の `foldWordsFrom` の内側のループ (26 バイト) は 32 バイトの境界をまたぐようになった
  (Sandy Bridge 系の命令のキャッシュは 32 バイト単位)。実行する仕事が増えたベンチはないので受け入れる。ループの先頭を 32 バイトに揃えると string-split は前より速くなるが、
  binary-search が 8.7% 遅くなるので、揃え方は変えない (FEAT-1018)。
