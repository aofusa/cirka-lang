## 概要

支援ライブラリのバイトの探索 (`cirka_bytes_index`。`indexOf` / `indexOfChar` / `lines` / `foldLines` / `splitOn` などが使う) は、
範囲の検査の後に C ライブラリの `memchr` を呼ぶ (FEAT-0097)。HTTP サーバの 1 要求では要求の終わり (`\r\n\r\n`) の 1 バイト目を
2 回探し、`memchr` は呼び出しごとに 3 本、合わせて 6 本の実行するコードのキャッシュライン (1 要求の 90 本のうち。Rust は 41 本) と
58 命令を使う。探す範囲は 32 バイトと 17 バイトである。string-split でも `memchr` は命令の 10% を占め、探す行や語は短い。

探索を生成するコードに展開する: 16 バイトずつベクトルで比べ (SSE2 の `pcmpeqb` / `pmovmskb`)、残りが 16 バイトより短くなったら
`j` で終わる 16 バイトを比べる (その前のレーンは比べ済みで一致しない)。64 バイトを比べても見つからない長い探索だけ、残りを
`memchr` に任せる。16 バイトより短い範囲は、文字列の中の 16 バイト (`min(i, len - 16)` から) を読んで範囲の外のレーンを捨て、
16 バイトより短い文字列は 1 バイトずつ比べる。読み込みはすべて `[0, len)` の中で、オブジェクトの外を読まない。

## メモ

- 実行テスト `tests/cirkalang/run/v007/string_search_paths.cirka`: 16 バイトより短い文字列のすべての範囲と印の位置、長い文字列の
  16 バイトの区切りと 64 バイトの前後の範囲、2 バイトのパターンの結果を、1 バイトずつの素朴な探索と比べる。
- 計測 (Docker、i5-3320M、FEAT-1017 との交互の 5 回の中央値。`docs/artifacts/f1022`): HTTP サーバの 1 要求の命令数 948 → 925、
  スループット 0.997 倍 (16 接続)・1.009 倍 (64 接続)。展開した 4 つの比較とその出口が並び、1 要求で実行するコードのキャッシュラインは
  かえって増えた (lackey、1 要求あたり 86.6 → 90.0 本。FEAT-1025 で比較をループに戻して詰め、FEAT-1017 の 86.6 本から 78.7 本に
  減った)。
- 全ベンチ (FEAT-1019〜1022 をまとめて FEAT-1017 と交互に 15 回、binary-trees は 5 回): cli-grep 0.900 倍・string-split 0.912 倍
  (行と語の短い探索)、ほかは ±2 % (binary-trees 1.020・session 1.015 倍は、FEAT-1027・1028 を含む最終の計測で FEAT-1017 より速い)。
  出力はすべて同じ。
