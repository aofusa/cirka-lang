## 概要

`bench/cli-grep` (Rust の 1.37 倍) を段階に分けて計ると (`getrusage`)、差の約半分はカーネルの時間で、ページフォールトの回数が
Rust の約 3 倍ある。テキストを作る段階で 19,121 回 (Rust 5,482 回)、ファイルの書き出しと読み込みまでで 32,657 回 (Rust 10,856 回)、
全体のシステム時間は 78 ミリ秒 (Rust 36 ミリ秒)。原因は大きな文字列の確保の仕方にある。

- `Data.String` の Builder は容量が足りないと新しい文字列を確保して全体を複写する。大きな確保は `malloc` (mmap) の新しいページなので、
  伸長のたびに複写した分と以後に書く分がページフォールトになる (最終的な容量の約 2 倍)。Rust の `String` は `realloc` で伸ばし、
  glibc は mmap の塊を `mremap` で動かす (複写もフォールトもない)。
- `build` は使った範囲をもう一度新しい文字列に複写する (cli-grep で 22 MB)。
- `readFile` (`cirka_fd_read` の上限なしの読み込み) は 4 KB から倍々に伸ばす一時領域に読み、最後に BYTES に複写する。
  Rust はファイルの大きさ (`fstat`) で 1 回だけ確保して直接読む。

Core と MIR に一意な BYTES をその場で伸縮する基本演算 `bytes_resize` を加え、これらを書き直す。

## 作業内容

- [x] Core / MIR の基本演算 `bytes_resize b n`: `b` を消費し、長さ `max(n, 0)` の BYTES を返す。先頭の `min(len b, n)` バイトは `b` の内容で、
  伸ばした部分は 0。`b` が一意 (RC == 1) で `malloc` の塊ならその場で `realloc` し、そうでなければ新しく確保して複写する
  (共有されていれば `b` の参照を 1 つ返す)。縮めるときは長さだけを変え、確保の半分未満になる `malloc` の塊は `realloc` で縮める
- [x] ランタイム `cirka_bytes_resize`、MIR インタプリタ、LLVM IR の生成。一意なオブジェクトの伸縮は、その場でも複写でも
  確保 1 回と解放 1 回として数える (ランタイムの種類と MIR インタプリタで確保と解放の数が一致する)
- [x] `Data.String`: Builder の伸長を `bytes_resize` で行う。伸長は呼び出しのまま残し (自己再帰)、容量の検査だけの `reserve` は
  呼び出し側にインライン化される。`build` は複写せずに長さを縮める
- [x] `cirka_fd_read` (上限なし、標準入力以外): 通常のファイルは `fstat` の大きさ (+1 バイト) の塊を `malloc` し、BYTES の頭と長さの
  16 バイトを空けて直接読む (それ以外は 4 KiB から)。足りなければ `realloc` で倍に伸ばし、読み終えた塊をそのまま BYTES にする
  (`bytes::adopt`: 使ったのが半分未満なら `realloc` で縮める。256 バイト以下の結果と検査用ランタイムでは複写する)。確保は従来どおり 1 回と数える
- [x] テスト: ランタイムの単体テスト (伸長・縮小・共有の複写・大きな塊)、MIR インタプリタとネイティブの実行テスト、
  CirkaLang の実行テスト (Builder への多数の追加と `build`、ファイルの読み書き)
- [x] 全ベンチを計測して記録する (ページフォールトの回数とシステム時間も)
- [x] ランタイムの `dealloc` を `#[inline(always)]` にする (下のメモ)

## メモ

- 計測 (FEAT-0095 の版との比較。11 題材を交互に 11 回ずつ実行した中央値の比、負荷 1.5 未満。binary-trees は 5 回):
  cli-grep 0.877 (0.258 → 0.226 秒、Rust との比 1.37 → 1.22)、string-split 0.939 (0.244 → 0.229 秒、Rust との比 1.24 → 1.19)。
  ほかの題材は誤差の範囲 (0.97〜1.00、session は従来どおり揺れる)。全題材の出力は変わらない。
- `getrusage` (7 回の最良): cli-grep のページフォールト 32,672 → 13,771 回 (Rust 10,854 回)、システム時間 65 → 36 ミリ秒
  (Rust 34 ミリ秒)。string-split は 19,153 → 8,411 回 (Rust 5,479 回)、25 → 14 ミリ秒 (Rust 9 ミリ秒)。カーネルの時間の差は
  ほぼなくなり、残る差はユーザー時間 (cli-grep 181 ミリ秒、Rust 138 ミリ秒): 1 回ごとのバイト操作の呼び出し (FEAT-0097)。
- 最初の計測で binary-trees が 8 % 遅くなった。生成コードは同じ (LLVM IR の差は `cirka_bytes_resize` の宣言だけ) で、
  ランタイムに加えたコードで LLVM のインライン化の判断が変わり、`cirka_free_raw` から `dealloc` が呼び出しになっていた
  (`release` が逆にインライン化された)。`dealloc` (呼び出し元は `release` と `cirka_free_raw` だけ) を `#[inline(always)]` にして
  元の形に戻した (binary-trees 0.989)。
- valgrind (`CIRKA_ALLOC=system` / `region`) で `builder_resize` の実行にメモリの誤りがないことを確かめた。その際、
  `scripts/memcheck.sh` が実行テストを valgrind の下で走らせていないことを見つけた (BUG-0038)。
- 読み込みの塊を BYTES 自体にする (`adopt`) のは、確保の数え方を MIR インタプリタ (読み込みの結果を確保 1 回と数える) と
  合わせるため。`bytes::resize` で伸ばすと伸長ごとに確保と解放が 1 回ずつ増え、テストの数の比較が合わない。
