# FEAT-0086: サーバの要求ごとの確保を減らす (継続・Result・文字列のビュー)

## 概要

CirkaLang v0.0.5 の HTTP サーバのベンチ (`bench/http-server`) は、並行な接続で Rust の 0.78 倍のスループット (時間で 1.28 倍) だった。
システムコールの数は同じで、差はユーザ空間の命令数 (1 要求あたり約 5,100 と約 700) にあり、その半分以上が確保と解放
(1 要求あたり 15〜20 回) である。要求ごとの確保を除き、Rust と同等のスループットを目指す (第二段階の目標は Rust 以上)。

## 作業内容

- [x] 1 要求の確保を数えて内訳を記録する (デバッグ用ランタイムの統計か callgrind)
- [x] 継続を受け取る関数 (`recvOn`・`sendFrom`) を、継続が分かっている呼び出しへ特殊化する (待たずに済んだときに継続のクロージャと
      `Ok d`・`MkTcpStream h` の箱を作らない)
- [x] `Str` のビュー・`Maybe Int` の結果を、worker/wrapper で箱なしにする (FEAT-0082 と共通)
- [x] サーバのサンプルの書き方 (連結 `out ++ hello`・残りの複製 `S.fromStr`) を見直し、ライブラリに要るもの (出力のバッファなど) を加える
- [x] 効果を `bench/http-server/run.sh` で計測しチケットに記録する (16-performance.md §4)

## 受け入れ条件

- [x] `bench/http-server` の 16・64 接続のスループットが Rust の 0.9 倍以上
- [x] テストを追加し `scripts/ci.sh` が通る

## メモ

- FEAT-0243 の計測 (callgrind、16 接続 × 500 要求): 確保と解放 (valgrind の下ではランタイムのアロケータが `malloc` に切り替わる) が
  命令の半分以上。ほかは `step` の文字列処理 (9.7%)、バイト列の複製 (6.3%)、`recvOn` (2.4%)。
- 待ちの張り直し (`EPOLLONESHOT` と `EPOLL_CTL_MOD`) は、読んで `EAGAIN` になったときだけ行う。負荷の高いときの回数は perf が使えず
  数えていない (strace の下ではサーバが遅く、ほとんど待たない)。
- 2026-11-26 の状況 (FEAT-1000〜1031 の後。Docker、`docs/artifacts/f0086`):
  - 1 要求の確保: 2 回 (valgrind の下、`CIRKA_ALLOC=system` で `malloc` の数を 2,000 要求と 20,000 要求の実行の差から数えた。
    Rust のサーバは 0 回)。callgrind の呼び出し元は、応答を送った後の待ちの継続のクロージャ (`Std.Net.sendFrom$io$f1$w$k0` の
    `mkclosure`。応答を送った直後には次の要求が届いていないので、受信は空とわかっていて待ちに入る) と、受け取ったバイトの BYTES
    (`cirka_sock_recv`。スレッドの受信バッファから写す) の 1 回ずつ。どちらもインラインの空きリストからの確保 (FEAT-1027) で、
    v0.0.5 の 15〜20 回はほかに残っていない。
  - 継続の特殊化: 静的な引数の特殊化 (FEAT-0061、`sat.rs`) が、`recvOn`・`sendFrom` を継続の分かった呼び出しごとに写す
    (`recvOn$io$f2$w`・`sendFrom$io$f1$w$k0`。`$k0` は送り始めの位置 0 の写し、FEAT-0094)。待たずに済んだときは継続のクロージャも
    `Ok d`・`MkTcpStream h` の箱も作らず、送信の後の受信から `answer` へ直接進む。
  - ビューと結果: `answer` (`step` の `S.indexOf` の `Maybe Int`・`S.drop` のビュー・`Reply`) は何も確保しない (和の CPR と積の
    合流点、FEAT-1008・1009・1012)。
  - サンプルの書き方: `out ++ hello` は `out` が空なら `hello` を返し (FEAT-1003)、`S.fromStr` の空の残りは静的な空文字列なので、
    書き方を変える必要も、出力のバッファを加える必要もない。
  - `bench/http-server/run.sh` は CirkaLang の回をすべて終えてから Rust の回を走らせていたので、計測の途中で機械の負荷が変わると
    差になって現れた (16 接続 0.70 倍・64 接続 0.83 倍と出た。同じ時間帯に FEAT-1031 の版・main の版・Rust を順を回して交互に
    9 回ずつ走らせると、main / FEAT-1031 の版は 1.009・1.043 で、遅くなってはいない)。回ごとに 2 つのサーバを交互に (先に走る方を
    入れ替えて) 走らせ、中央値と同じ回の比の中央値を出すように改めた。
  - `run.sh` (`CIRKA_BENCH_RUNS=9`、20 万要求): Rust / CirkaLang のスループットの比の中央値は 1 接続 1.021・16 接続 1.007・
    64 接続 1.010 (CirkaLang は Rust の 0.98〜0.99 倍)。スループットの中央値は 1 接続 13,740 / 13,903 要求/s、16 接続 24,639 / 25,033、
    64 接続 24,173 / 24,423、最大 RSS は 2.5 MiB / 2.2 MiB。この日は回ごとの揺らぎが大きく (同じサーバで 13,000〜28,000 要求/s)、
    比は FEAT-0091 の計測 (0.995 / 1.005) と同じく 1.00 ± 0.01 の範囲にある。
  - 残る 2 回の確保をなくすには、待ちの継続を記述子ごとに使い回す (ループが呼んだ継続の領域を次の待ちに渡す) か、受信を
    接続ごとのバッファに直接読む必要がある。2 回の確保と解放はインラインの空きリストの操作とバイトの写しで、1 要求の命令 (827) の
    1 割に満たないと見積もる。HTTP サーバの時間の 9 割はカーネル (FEAT-0091 のメモ) で、なくしても 1 要求の CPU 時間の 1 % に
    届かないので、ここでは行わない。
  - 実装は FEAT-1001〜1031 で行い、テストもそれぞれのチケットで加えた (`scripts/ci.sh` は BUG-0044 の後に通った)。このチケットで
    変えたのは計測のスクリプト (`bench/http-server/run.sh`) だけ。
