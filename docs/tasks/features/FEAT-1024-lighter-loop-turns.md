## 概要

イベントループは `epoll_wait` の 1 回りごとに、他のスレッドからの受け箱 (投稿された動作・ブロッキングの仕事) をロックを取って
空にし (`run_inbox`)、時計を読んでタイマーを走らせ (`run_timers`)、もう一度ロックを取って受け箱の状態を読む (`inbox_state`)。
受け箱もタイマーも使わないプログラム (HTTP サーバ) でも、1 回りに `pthread_mutex_lock` / `unlock` を 2 組、`free(NULL)` を 2 回、
`clock_gettime` を 1 回呼ぶ。1 回りの要求は 8 前後なので命令数は小さいが、C ライブラリと vDSO の 4 ページ (と vDSO のデータ) の
コードを回りごとに実行する。

- 受け箱に `pending` (= 積まれた動作の数 + 走っているブロッキングの仕事の数) を原子的な値で持つ。ロックの中で両方が変わるたびに
  書き、ループのスレッドはロックを取らずに読んで、0 なら受け箱の処理を飛ばす。0 を読んだ後に積まれた動作は、これまでと同じく
  eventfd でループを起こす。
- タイマーのヒープが空ならタイマーを走らせず、時計を読まない。
- 一度も伸ばしていない (null の) バッファの解放で `free` を呼ばない。

## メモ

- HTTP サーバの callgrind で、ループの 1 回り (要求の約 8 回に 1 回) ごとの `pthread_mutex_lock` / `unlock`・`free`・
  `clock_gettime` の呼び出しがなくなった (要求あたり 0.126・0.126・0.063 回 → 0)。命令数は 905 → 896。
- 計測 (Docker、FEAT-1022 との交互の 5 回の中央値。`docs/artifacts/f1026`): スループット 1.003 倍 (16 接続)・1.000 倍 (64 接続)。
  binary-trees は FEAT-1023 と同じ (1.103 倍、FEAT-1017 比。FEAT-1023 のメモ)。
