## 概要

`cirka_bytes_from` (受信したバイト・数の文字列・ファイルから読んだ行など、バッファから文字列を作る) は `memcpy` で写す。
短い写しでも C ライブラリの関数の入口と長さの分岐を通り、そのコードは C ライブラリの別のページにある (HTTP サーバでは要求ごとに
約 40 バイトの要求を写し、`memcpy` の 4 本のキャッシュラインと 1 ページを実行する。FEAT-1019 で `memchr` がなくなると、
要求ごとに触る C ライブラリのページはこれだけになる)。

64 バイトまでは、両端から重ねた 16 バイト (短ければ 8・4・1 バイト) の読み書きで写す (glibc の `memcpy` の短い場合と同じ方法)。
読み書きはどちらの側も `len` バイトの中だけで行う。長い写しは `memcpy` のまま。

## メモ

- HTTP サーバの 1 要求の命令数 925 → 905 (`memcpy` の入口と長さの分岐がなくなった)。要求ごとに C ライブラリのコードを
  実行しなくなった (lackey のコードのページ 11.1 → 10.1、FEAT-1017 比)。
- 計測 (Docker、FEAT-1017 との交互の 5 回の中央値。`docs/artifacts/f1022`): スループット 1.009 倍 (16 接続)・1.020 倍 (64 接続)。
  Rust に対して 1.023 倍 (16 接続)・1.015 倍 (64 接続) 遅い (FEAT-1017 では 1.027・1.035 倍)。全ベンチは FEAT-1019 のメモ。
- 16〜64 バイトの写しは FEAT-1028 で 1 つの経路にした (先頭と末尾の 16 バイト、32 バイトを超えたら 2 番目と最後から 2 番目)。
