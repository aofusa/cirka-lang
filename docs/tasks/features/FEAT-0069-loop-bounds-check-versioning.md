- 優先度: P1
- 依存: FEAT-0063, FEAT-0067

## 概要

FEAT-0067・0068 の後で Rust の 1.5 倍 (G3) を超えるのは n-body `own.chs` (0.705 s / Rust 0.389 s、1.81 倍) と
fannkuch-redux `own.chs` (0.405 s / 0.235 s、1.72 倍)。原因を調べた (計測はメモ)。

- n-body の命令数は Rust の 2.2 倍 (1 ステップ 1,003 / 455)。生成 IR から境界検査の分岐を手で除くと
  命令数 38 % 減 (501 M → 309 M)、時間 0.714 → 0.580 s。最初の反復を一意性検査のある関数で回すこと (FEAT-0067) の
  分は 7 % 減・4 % 程度で小さい。
- fannkuch-redux も境界検査を除くと 0.407 → 0.280 s (Rust 0.230 s)。array-sort も partition の境界検査が約 0.035 s。
- 境界検査は配列の読み書きのたびに長さの load・比較・分岐を払う。添字はループの変数の一次式で、ループの条件
  (`i >= 5` で抜ける等) と入口の値から常に範囲内だと分かるが、配列の長さは実行時にしか分からない (n-body は 35)。
- LLVM の IRCE・loop predication (既定のパイプラインにない) を足しても 1 つも除かれなかった (自己末尾呼び出しの
  ループは入れ子の状態機械になり、帰納変数の形にならない)。

証明 (FEAT-0234 / FEAT-0154) がなくても、検査そのものを入口に集めれば意味を変えずに除ける。MIR に次のパスを作る。

- 自己末尾呼び出しを持つ関数 `f` について、整数の引数と配列の引数の長さの間の差分制約 (`i >= 0`、`i <= j`、`hi < len(a)`、
  `len(a) >= 35` など) の候補から、自己末尾呼び出しで保たれる (帰納的な) ものを残す (Houdini 法)。本体はガード
  (比較と `switch`) を経路の条件として、差分制約 (DBM) と定数倍の区間で解析する。整数の加算は桁あふれしないと分かるときだけ
  一次式として扱う (`Int` は 2 の補数で桁あふれする)。
- 前提条件 `P` のもとで必ず成り立つ検査を除いた写し `f$b` を作り、その自己末尾呼び出しは `f$b` に向ける。`f` の入口で `P` を
  1 回だけ確かめ、成り立てば `f$b` に移る。成り立たなければ元のとおり検査しながら回る。`P` が成り立つ反復ではもともと検査が
  失敗しないので、意味 (どの検査がいつ panic するか) は変わらない。
- 検査を除いた読み書きは MIR の別のプリミティブ (`bytes_get_f64_unchecked` など) で表す。インタプリタはその添字が範囲外なら
  内部エラーにし (実行テストが解析の誤りを捕まえる)、`--runtime=debug` のコード生成は検査を残す (16-performance.md §3)。

## メモ

### 調査 (2026-11-07)

n-body `own.chs` の 500,000 ステップを callgrind (Docker) で計測した。

| | 命令数 | 条件分岐 | 予測ミス (callgrind の模型) |
|---|---:|---:|---:|
| `own.chs` | 501.4 M | 74.6 M | 3.5 M |
| Rust | 227.8 M | 0.56 M | 5.3 K |

関数ごと (`own.chs`): `steps$pairs$w$u` 342.5 M (分岐 46 M)、`steps$move$w$u` 70.5 M、`steps$pairs$w` 59.0 M、
`steps$move$w` 23.5 M。Rust は 5 体のループを完全に展開し、配列の長さが型で決まるので境界検査がない。
`pairs$w$u` の内側のループ (1 組) は 64 命令のうち 19 命令が境界検査 (8 回の比較と分岐)。

生成 IR を手で変えた版 (5,000,000 ステップ、時間は wait4 の最良値):

| 版 | 命令数 (500,000) | 時間 |
|----|---:|---:|
| 元 | 501.4 M | 0.714 s |
| 境界検査なし | 309.4 M | 0.580 s |
| `steps` から `$u` の関数を直接呼ぶ | 467.9 M | 0.683 s |
| 両方 | 297.4 M | 0.634 s |
| Rust | 227.8 M | 0.386 s |

- 境界検査をなくすと LLVM が `move` のループを `steps` に展開し、`pairs` の 1 組も 46 命令になる (Rust は 1 組約 40 命令)。
- 「両方」が「境界検査なし」より遅いのは配置の影響 (命令数は少ない)。
- fannkuch-redux (10): 元 0.407 s、境界検査なし 0.280 s、Rust 0.230 s。
- LLVM 18 の `irce`・`loop-predication` を `default<O2>` の後に足しても、panic の呼び出しは n-body 231 → 231、
  fannkuch-redux 168 → 168 で 1 つも減らなかった。

### 実装 (2026-11-08)

- MIR に検査なしの読み書き 11 種 (`bytes_get_i64_unchecked` など) と `is_value` を加えた。検証器は検査ありのものと同じ型で扱う。
  インタプリタは範囲外の検査なしアクセスを内部エラーにし、`--runtime=debug` のコード生成は検査を残して
  `internal error: unchecked index out of bounds` と報告する。
- 前提条件の候補の選び方 (`bounds.rs`):
  1. 非負 (`x >= 0`) を矛盾しない限り入れ、Houdini 法で帰納的なものを残す。
  2. 添字と比較に使われる整数の引数と長さの関係 (`x <= len`、`x < len`、`x <= y`、`x < y`、弱い方を先に) から、証明できる検査を
     最も増やす 1 つ (なければ 2 つの組) を加えることを繰り返す。最初は全部の候補を順に入れていた (`grow`) が、帰納的だが役に立たない
     `hi < i` が先に入り、partition の `i <= j` と矛盾して締め出された (配列の要素 `u[i]` の検査が残った)。
     2 つの組は `i == n` で止まるループ (`i <= n` と `n <= len` が揃って初めて証明できる) のため。`!=` の比較は `a <= b` が分かって
     いれば `a < b` として使う。
  3. 残る検査の添字の上限から `len >= c` を加える。
  4. 証明に要らない原子を除く (強い原子・引数どうしの関係から試す)。`P` が弱く少ないほど入口で成り立ちやすい。
- 前提条件なしで成り立つ検査 (ループ自身が `0 <= i < len` を比べる、同じ添字の 2 度目のアクセス) は写しを作らず `f` の中で除く。
  CirkaLang の `Prelude.parseDigits` で空の `P` になり、入口の検査の生成が内部エラーになっていたのを、この扱いで直した。
- `force` を通して使う (遅延の) 配列の引数も対象にした。入口でまず `is_value` で値か確かめ (評価はしない)、値なら長さを読む。
  サンクを受け取ったループは最初の反復を検査ありで回してそこで評価し、次の反復の入口で `f$b` に移る。spectral-norm の `mul`、
  array-sort の `check`、fannkuch-redux の `copy`、n-body の最初の反復の関数 (`steps$pairs$w` など) がこれで対象になった。
- テストを書く中で、結果に名前のない書き込み (`let _ = prim bytes_set_i64(..)`) の検査を解析が読み飛ばし、到達しない (除ける) 検査と
  扱っていた誤りを見つけて直した (回帰テスト `bounds_checks_without_a_proof_stay`)。

### テスト

- MIR の単体テスト (`crates/cirka-mir/src/tests.rs`): fill (3 通りのループの条件と `i == n`)、partition、n-body の形 (定数の長さ、
  `2 * i < 10` の切り捨て、定数の添字)、両端からのループと 0 までの減少、配列全体 (`bytes_len / 8`・`array_len`)、遅延の配列 (サンク、
  評価済みのサンク = 間接参照、panic するサンクを評価しないこと)、前提条件なしで除ける検査。除いてはならない検査として、配列から
  読んだ添字、名前のない書き込み、毎回別の配列を読むループ、新しい配列に置き換わるループ、`bytes_len / 4`、負の係数、
  `i + 1`・`i * 2^32` の桁あふれ。どれも変換後の MIR が検証器を通り、インタプリタで元と同じ出力・panic・確保回数になることを確かめる。
- 実行テスト: `tests/achc/run/h3/bounds_loops.hs` (前提条件が成り立つ・入口で成り立たないが範囲内で終わるループ)、
  `bounds_overrun.hs` (配列の終わりを越える)、`bounds_negative.hs` (負の添字から始まる) が元と同じメッセージで panic する。
- コード生成: 検査なしの読み書きはリリースのランタイムで検査を出さず、デバッグのランタイムでは内部エラーの検査を出す。

### 変異テスト

解析に誤りを入れた 36 通りの変異 (加算・乗算の桁あふれの判定を外す、負の係数を許す、別の配列を同じ長さとみなす、`switch` の既定の腕の
条件を逆にする、比較の定数をずらす、`lshr` の量を見ない、入口の検査の `lshr`・`lt`・`and` を変える、`is_value` が間接参照を値と
みなす、自己末尾呼び出し以外も写しへ向ける、すべての検査を除く、など) で MIR の単体テストを走らせた。31 通りでテストが失敗し、
健全性を壊す変異はすべてここに入る。残る 5 通りは仮定を弱める (`<=`・`>`・`==`・長さの下限・切り上げの丸め) だけで、
検査が除かれにくくなるが誤りにはならない。

### 残る課題

- CirkaLang の比較は `Bool` の構築子になり join を通した `switch` で分岐するので、ループの条件が解析に見えない
  (`Prelude.parseDigits` の最初のアクセスが残る)。CirkaLang の Core 最適化 (case-of-case・既知の構築子) で消すのが本筋。
- 定数のずれのある候補がない: `a[i + 3]` を `i < n` で守るループの `n + 3 <= len`、`a[i - 1]` の `1 <= i` (ステンシル)。
  `7 * i >= 35` のように乗算の結果だけを比べるループも、`i` の上限がないと積が桁あふれしうるので証明できない。
- 3 つの値の関係 (CirkaLang の `bytes_copy` の `dst[off + i]` に要る `off + n <= len`) は差分制約で表せない。
