## 概要

生成コードの確保 (`alloc`、クロージャとサンクの作成) と解放 (drop 特殊化で `rc == 1` のセルの解放、一意な環境のクロージャの呼び出しでの
環境の解放) は、毎回ランタイムの関数 (`cirka_alloc` / `cirka_free_raw`) を呼んでいた。どちらもスレッドのフリーリストの先頭を出し入れする
だけの短い経路だが、呼び出しと戻り・レジスタの受け渡しに加えて、ランタイムの別のキャッシュラインのコードを通る。受信が空のときに読む
`cirka_errno` も同じ。07-backend.md の設計 (フリーリストの高速経路を生成コードにインライン化する) をここで実装する。

- 確保: 256 バイト以下の大きさの決まったオブジェクトは、スレッドの状態 (TLS ブロック `cirka_tls_block`、local-exec) のそのクラスの
  フリーリストから先頭を外し、`allocs` を 1 つ増やす。リストが空ならランタイムの `cirka_alloc` を呼ぶ (起こりにくい重み)。
- 解放: 大きさのわかるセル (drop 特殊化の `rc == 1` のセル、一意な環境のクロージャの環境) は、スレッドの状態の `free_fast` が 1 なら
  そのクラスのフリーリストに積み、`max_live` と `frees` を更新する。0 ならランタイムの `cirka_free_raw` を呼ぶ。`free_fast` は、その
  スレッドでランタイムの解放が領域 (方式 1) のオブジェクトを解放したときに 1 になる。方式 1 では小さなオブジェクトはすべて領域から
  確保されるので、生成コードが積むセルはどれも領域のもの。方式 2 (`CIRKA_ALLOC=system`、valgrind の下) と、まだランタイムで何も解放して
  いないスレッドは 0 のままで、`malloc` のオブジェクトがフリーリストに入ることはない。
- 統計: 確保は `allocs` を増やすだけにし、`max_live` (生きている数の最大、目安) は解放の直前の生きている数 (`allocs - frees`) で
  更新する (ランタイムの確保と解放も同じ)。
- `errno`: `cirka_errno` の呼び出しは、スレッドの状態に `errno` のアドレス (FEAT-1021) があればそこから読み、なければ呼ぶ。
- 検査付きのランタイム (`debug_rt`) ではどれもインラインにしない (生存表の検査を通す)。生成コードが読む TLS ブロックのオフセット
  (フリーリスト・`allocs`・`frees`・`max_live`・`free_fast`・`errno` のアドレス) はランタイムのテストで固定する。

## メモ

- binary-trees (Docker、5 回を交互に実行した中央値): FEAT-1026 22.61 秒 → 確保のインライン化 20.23 秒 (0.894) → 解放も 17.74 秒
  (0.784)。命令数 (深さ 16、callgrind): 1,464.7M → 1,194.7M → 1,044.8M。
- HTTP サーバの 1 要求の命令数: 912 → 881 (確保と `errno`) → 872 (解放も)。Rust は 668。
- HTTP サーバのスループット (FEAT-1026 と交互の 7 回の中央値): 確保のインライン化 1.002 倍 (16 接続)・0.996 倍 (64 接続)、解放も
  0.999 倍・1.002 倍 (誤差の範囲。時間の 9 割はカーネル)。
- `CIRKA_ALLOC=system` (valgrind の実行テスト) では `free_fast` が 0 のままで、生成コードの解放はすべて `cirka_free_raw` を呼ぶ
  (`malloc` の塊がフリーリストに入らない)。
- 全ベンチは FEAT-1028 までをまとめた最終の計測 (FEAT-0091 のメモ)。
