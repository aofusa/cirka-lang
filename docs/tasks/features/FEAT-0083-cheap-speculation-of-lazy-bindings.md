## 概要

遅延 `let` の右辺が **安価で、失敗も発散も副作用もない** 計算 (失敗しないプリミティブ演算・正格フィールドの構築子・評価済みの変数の
`case`・純粋な libm 関数) なら、サンクを作らずに先に評価する (GHC の `exprOkForSpeculation` に当たる投機的評価)。
評価しても意味は変わらず (値は同じで、失敗しない)、サンクの確保と `force` がなくなる。

FEAT-0061 の調査で、n-body `plain.hs` の `interactAll` が 1 組ごとに 3 つのサンク (自由変数 12 個) を作っていることが分かった:
`pairStep` の組の要素 (`B x y z (vx - dx * mj) …`) と共有の `mag = dt / (d2 * sqrt d2)` が遅延になる。
どれも浮動小数点の算術と `sqrt` だけで、7 フィールドの `B` を直接作る方がサンク (12 フィールド) より小さい。
aCHC `plain.hs` は GHC -O2 の 2.46 倍 (bench-report.md「遅延の意味論の修正」) で、この差の一因と見られる。

## 作業内容

- [x] 先行評価してよい式の判定 (`ww::speculatable` の一般化): 大きさの上限、失敗しないプリミティブ演算 (浮動小数点の除算を含む)、
      正格フィールドの構築子 (フィールドも同じ条件)、評価済みの変数の `case`、純粋と分かっている `extern` (libm の `sqrt` など)
- [x] 遅延 `let` をその条件で `let!` にするパス (BUG-0014 の意味論を壊さない: 失敗しうる計算・呼び出しは遅延のまま)
- [x] n-body `plain.hs` のサンクの数と時間を前後で計測し、ほかのベンチの IR の変化を確かめる

## 受け入れ条件

- [x] 先行評価する式としない式 (失敗しうる除算・呼び出し・大きい式) のユニットテスト
- [x] `-- max-forced:` などで n-body 型のループのサンクがなくなることを確かめる run テスト
- [x] テストを追加し `scripts/ci.sh` が通る

## メモ

### 実装

- 判定は `cirka-core` の `ww::Spec::ok` (GHC の `exprOkForSpeculation`)。評価済みの変数 (unboxed の引数・すべての呼び出しが評価済みで渡す引数・
  `let!` と `case` の束縛子・正格フィールド)、失敗しないプリミティブ演算 (`total_prim`、浮動小数点の除算を含む)、名前と型が一致する純粋な C 関数
  (`ww::PURE_EXTERNS`: libm の `sqrt`・`sin` など。同名で型の違う外部関数は対象外)、正格フィールドの構築子、`case`、`let!`、値の `let` だけの式で、
  大きさは 48 ノードまで (W/W が評価済みの引数として扱うのは 24 ノードまで)。
- パスは `strict::speculate`。float-in の後、最後の W/W の前に 1 回。ω の遅延 `let` を `let!` にし、ω の仮引数への引数と遅延フィールドへの引数は
  新しい変数 `sp` に `let!` で束縛する。値 (ラムダ・リテラル) と、下ろしでそのまま作られる構築子 (正格フィールドが原子) は対象外。
- 付随: `CallWalk::is_value` を MIR の `builds_now` と一致させた (正格フィールドの引数が安全なときだけ値。BUG-0014 の意味論)。
  unboxed のラムダ引数・unboxed の遅延 `let`・正格フィールドの束縛子を評価済みとして扱う。
- 借用推論 (ADR-085、`cirka-mir/src/borrow.rs` の `owned_by_callers`): 先行評価で binary-trees の `check` の worker の `force` が消えて引数が借用になり、
  呼び出し側の解放の走査で 1.5 倍に悪化した。不動点の後、すべての呼び出しが所有値の最後の使用 (または分解するだけの所有値のフィールド) を渡す
  借用引数を owned にする (呼び出し元の引数が同じ規則で owned になる場合を含む最大不動点。サンクの関数の引数は評価が手放す)。
  文字列リテラルを渡す呼び出しがあれば借用のまま (string-split の命令数が 8% 増えたため)。
- 既知の費用: 最後の使用で渡す値が他から共有されている (CAF など) と、owned の走査は要素ごとに `dup`/`drop` をする (借用なら 0 回)。
  現在のベンチにこの形はなく、計測していない。必要になれば、共有を見つけた時点で借用版に切り替える写しを検討する。
