# FEAT-1018: ループの先頭を 32 / 64 バイトに揃えるかを調べる

- 状態: done
- トラック: 共通基盤
- マイルストーン: SX 共通基盤の拡張 (各トラックの必要に応じて)
- 優先度: P2
- 依存: FEAT-1017, FEAT-0091
- 設計: [16-performance.md](../../design/16-performance.md)

## 概要

FEAT-1017 の計測で string-split が 1.4% 遅く見えたのは、実行する命令は関数ごとに同じで、熱い関数が 16 バイト前へずれ、
内側のループ (26 バイト) が 32 バイトの境界をまたいだためだった (Sandy Bridge / Ivy Bridge のデコード済みの命令のキャッシュは
32 バイトの区切りで命令を持つ)。LLVM の x86 の既定はループの先頭を 16 バイトに揃える。生成したコードのループの先頭を
32 / 64 バイトに揃えれば (clang の `-falign-loops=`)、こうした配置の揺れが減って速くなるかを調べ、採るかを決める。

## 作業内容

- [x] 全ベンチを FEAT-1017 の版の LLVM IR から `-falign-loops=32` と `-falign-loops=64` で作り直し、今の版と交互に実行して比べる

## 受け入れ条件

- [x] 採るかどうかを計測で決め、結果を残す (採らない。下のメモ)

## メモ

- 2026-11-26: 15 回の交互実行の中央値 (binary-trees は 5 回)、今の版 (16 バイト) に対する時間の比。出力はすべて同じ。

  | ベンチ | 32 バイト | 64 バイト |
  |---|---|---|
  | array-sort | 0.990 | 0.989 |
  | binary-search | 1.087 | 1.087 |
  | binary-trees | 1.006 | 0.996 |
  | cli-grep | 0.992 | 0.993 |
  | mandelbrot | 0.998 | 0.999 |
  | n-body | 0.998 | 1.001 |
  | spectral-norm | 0.993 | 0.994 |
  | stencil | 0.989 | 0.995 |
  | string-split | 0.975 | 0.983 |
  | effects | 0.997 | 0.995 |
  | session | 0.997 | 1.005 |

  string-split は 32 バイトで FEAT-1017 の前の版より速くなり、FEAT-1017 での差が配置によることを確かめた。6 つのベンチは
  0.5〜2.5% 速くなるが、binary-search が 8.7% 遅くなる。binary-search の内側のループは 32 バイトに揃えると 32 バイトの区切り
  2 つに収まり (16 バイトでは 3 つ)、ループ自体の配置は良くなる。探索ごとにループに入る前の 23 バイトの詰め物 (nop) を実行し、
  外側のループの配置も変わる。ハードウェアの性能カウンタを使えない環境では原因を一つに絞れない。一様に揃えることは採らず、
  16 バイトのままにする。
