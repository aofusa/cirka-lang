## 概要

サーバ用途のためのイベントループ (epoll、将来 io_uring) とタイマー。

## 作業内容

- [x] epoll ベースのリアクタ: スレッドごとのループ、1 度だけの待ち (`EPOLLONESHOT`) とコールバック、世代による古い事象の破棄、
      エラー・切断は待っていた事象も立てて知らせる、`cirka_loop_current` (`evloop.rs`)
- [x] ノンブロッキングソケット: TCP の listen / accept / connect (完了は `connect_result`) / send (`MSG_NOSIGNAL`) / shutdown / nodelay、
      名前解決、`cirka_fd_write_from`・`cirka_fd_set_nonblocking`・`cirka_fd_limit_raise`、ネットワークの errno の文言 (`net.rs`)
- [x] タイマー: スラブ (番号に世代) と期限の二分ヒープ、O(1) の取り消し
- [x] スレッドプールとの連携: `cirka_loop_blocking` (プールで実行し結果をループのスレッドへ)、ほかのスレッドからの post (`cirka_loop_remote`)。
      受け口は eventfd と mutex の待ち行列、受け口が生きている間はループが待つ
- [x] C ヘッダ (`cirka_rt.h`)・`.env.sample` (`CIRKA_POOL_THREADS`)・05-runtime.md §10・10-testing.md・ADR-087

## メモ

- 2026-11-14: 設計は ADR-087 と 05-runtime.md §10。グリーンスレッドや `async` は持たず、言語側の API (FEAT-0241) はコールバックの上に作る。
- 実装中に決めたこと:
  - コールバックはループを捕捉せず `cirka_loop_current` で得る。ループはコールバックを持つので、捕捉すると循環になり
    ループを捨てても解放されない (MIR のテストを書く中で、止めたループに待ちが残る場合を考えて気づいた)。
  - パイプの書き手が閉じると、データが残っていなければ epoll は `EPOLLHUP` だけを返し `EPOLLIN` を立てない (単体テストで発見)。
    読む待ちのコールバックが呼ばれても「読める」が立たないと扱いにくいので、エラー・切断は待っていた事象も立てる (libuv と同じ)。
  - ソケットへの書き込みは `send(MSG_NOSIGNAL)` の `cirka_net_send`。ランタイムは `SIGPIPE` の扱いを変えない。
    `write` で試して `ENOTSOCK` なら `send` という作りは、ファイルへの書き込みのたびにシステムコールが 1 つ増えるのでやめた
    (ソケットかどうかはライブラリの型で分かる)。
  - プールの仕事は待ち行列に入ってから終わるまで「動いているスレッド」に数え、結果を出した後は終わりかけに数える。
    数えないと、ループが終わった直後のプロセスの終了で、プールのスレッドがまだ触っているオブジェクトをリーク検査が読みうる。
  - 受け口が生きている間はループを終わらせない (チャネルの送り手と同じ)。最初は受け口を数えず、post を待たせるために
    長いタイマーを置いて最後の post で取り消すテストになっていた。ほかのスレッドからの結果を待つ使い方ではこの方が自然。
- 1 万同時接続のエコー (`echo_10k.mir`、1 スレッド・1 ループ): i5-3320M で 1 回約 1.1 秒 (接続・エコー・切断が 1 万ずつ)、
  確保 110085 回 (解放も同数)、最大 RSS 約 3 MB。接続中のクライアントを 256 までにする (待ち受けのキューは `somaxconn` = 4096 で、
  溢れると SYN が捨てられ 1 秒後の再送を待つ)。
  最初の版はクライアントが先に閉じ、1 回ごとに 1 万の TIME_WAIT がクライアントのエフェメラルポート (既定 28232 個) に残った。
  ループバックでは `tcp_tw_reuse=2` (既定) で再利用されて続けて実行しても通ったが、それに頼らないようサーバが先に閉じる手順にした
  (TIME_WAIT はサーバ側の 4 つ組に残り、クライアントのポートを使わない)。
- 受け口の意味を変えた後の `tests/mir/run/evloop.mir` を 4 構成 (debug・release・TSan・TSan + `CIRKA_ALLOC=system`) で各 15 回、
  ランタイムの単体テストを 5 回続けて実行し、失敗なし。
- Docker のコンテナの `scripts/ci.sh` で、`echo_10k.mir` (コンテナの記述子の soft 上限 1024 を hard まで上げて 2 万のソケット) と
  `evloop.mir` の TSan の構成を含めて通った。
- io_uring は扱わない (ADR-087 の代替案。epoll で 1 万接続の受け入れ条件を満たしたため)。必要になったら別チケットにする。
