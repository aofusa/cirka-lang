**依存型（Dependent Types）と証明のメリット**を、cirka-langの文脈（純粋関数型＋線形型による所有権・GCなし・高パフォーマンス）で整理します。

### 依存型とは（簡潔に）

通常の型は「値の種類」を表しますが、**依存型**は「値に依存した型」を書けます。

```idris
-- 長さがnのベクトル（Idris風）
data Vect : Nat -> Type -> Type where
  Nil  : Vect 0 a
  (::) : a -> Vect n a -> Vect (S n) a

-- 長さを保持したままappendできる
append : Vect n a -> Vect m a -> Vect (n + m) a
```

型そのものが「仕様」を表現でき、コンパイラがそれを検証します。

### cirka-langに入れる主なメリット

| メリット | 内容 | cirka-langとの相性 |
|----------|------|-------------------|
| **仕様の静的検証** | 「この関数はソート済みの配列を返す」「インデックスは範囲内」などを型で表現し、コンパイル時に保証 | 非常に高い。バグを実行前に潰せる |
| **メモリ安全性の強化** | 線形型（所有権）と組み合わせて「このポインタは有効な範囲内を指す」などを証明可能 | 相性抜群。Rustの所有権をさらに精密にできる |
| **不変条件の維持** | データ構造の不変条件（平衡木であること、など）を型で強制 | 純粋関数型なので証明が書きやすい |
| **ゼロコストの保証** | 証明部分は実行時に消去される（Idris 2のQuantitative Type Theoryのように） | パフォーマンスを落とさずに安全性を得られる |
| **ドキュメント兼仕様** | 型がそのまま仕様書になる。コメントより信頼性が高い | 長期的なメンテナンスに有利 |

### 具体的な嬉しい例（cirka-lang想定）

```haskell
-- 範囲が保証されたインデックスアクセス（依存型）
get : (i : Fin n) -> Vect n a -> a
-- Fin n は「0以上n未満の自然数」なので、範囲外アクセスが型レベルで不可能

-- 所有権と依存型の組み合わせ
-- 「このバッファはまだ解放されていない」かつ「サイズは正確」
type SafeBuffer (n : Nat) = OwnedPtr (Array n Word8)

-- 仕様：入力の合計を正しく計算する
sumSpec : (xs : Vect n Int) -> (sum xs ≡ fold (+) 0 xs)
-- これを証明すると、実装が仕様を満たしていることが保証される
```

- 配列の境界チェックを実行時ではなくコンパイル時に済ませられる。
- 「この関数を呼んだ後はファイルが必ず閉じられている」といった資源プロトコルを型で表現できる。
- 線形型だけでは表現しにくい「値の関係性」を追加で保証できる。

### パフォーマンス・GCなしとの関係

- **証明は実行時に消える**（erasure）。正しく設計すれば、依存型を入れても生成コードの速度やメモリ使用量はほとんど変わりません。
- Idris 2がまさにこの方向で、Quantitative Type Theoryにより「0（消去）」「1（線形）」「ω（無制限）」を統一的に扱っています。
- cirka-langでも「線形型で所有権を管理しつつ、依存型で値の性質を証明する」形にすれば、GCなし・高パフォーマンスを維持したまま正しさを強化できます。

### トレードオフ（正直なところ）

| 項目 | 影響 |
|------|------|
| **学習コスト** | 高い。証明の書き方を覚える必要がある |
| **コンパイル時間** | 長くなる傾向（特に複雑な証明） |
| **表現力** | 非常に高いが、すべてを依存型で書く必要はない |
| **実用性** | クリティカルな部分だけ依存型を使い、残りは通常の型で書く「段階的導入」が現実的 |

### cirka-langへの導入方針の提案

1. **最初はオプション**  
   依存型を言語の必須機能にはせず、拡張として導入する（Haskellの`DependentHaskell`やIdrisのように）。

2. **線形型との統合を優先**  
   Idris 2のQuantitative Type Theoryを参考に、「多重度（0/1/ω）」と依存型を一緒に設計すると、所有権と証明が綺麗に共存します。

3. **使いどころを絞る**  
   - 配列・バッファの境界安全性
   - プロトコル（ファイルやソケットの状態機械）
   - 数学的な性質が重要なライブラリ（`cirka-linalg`など）
   - 全コードを証明する必要はない。

4. **証明の負担を減らす工夫**  
   - 自動証明（SMTソルバー連携など）の検討
   - よく使うパターンはライブラリで証明済みのものを提供

### まとめ

依存型を入れる最大の価値は、**「GCなし・高パフォーマンス」に加えて、「このコードは仕様を満たしている」ことをコンパイラが保証してくれる**点です。

特にcirka-langのように所有権を型で管理する言語では、線形型（資源の正しい使用）と依存型（値の正しい性質）を組み合わせることで、かなり強い正しさを静的に得られます。

ただし、全機能を最初から入れる必要はありません。線形型と所有権モデルを固めた上で、依存型を「必要な場所で使える強力なツール」として追加するのが現実的です。

依存型をどの程度の優先度で検討したいか、または具体的に「こういう性質を証明したい」という例があれば、それに合わせた設計案をさらに掘り下げられます。
