**証明・仕様表現・正しさの保証に使える言語機能**を、cirka-langに取り込めそうなもの中心にまとめます。

すでに議論した依存型・線形型に加え、最近の言語や研究で実用的に使われているものを整理します。

### 特に有望な機能

| 機能 | 何ができるか | 代表例 | cirka-langへの適性 | 備考 |
|------|--------------|--------|-------------------|------|
| **Refinement Types（洗練型 / Liquid Types）** | 型に論理述語を付けて不変条件を表現。SMTで自動検証 | Liquid Haskell、Flux（Rust）、Liquid Java | ★★★★★ | 依存型より軽量。境界チェック・ソート済みリストなどを自動で保証しやすい |
| **Effect Systems / Algebraic Effects** | 副作用を型で追跡。ハンドラで制御 | Koka、OCaml 5、Effekt、Unison | ★★★★☆ | 純粋性と副作用を明確に分離。KokaはPerceusでGCなしに近い参照カウントも実現 |
| **Session Types** | 通信プロトコルを型で表現し、デッドロックフリーなどを保証 | 線形論理ベースの研究、Scala実装など | ★★★★ | 線形型と相性が良い。ネットワークや並行処理の仕様保証に強い |
| **Contracts / Pre-Post Conditions** | 関数の前後条件・ループ不変条件を書いて検証 | Dafny、SPARK（Ada）、Verus（Rust） | ★★★★☆ | 実装と仕様を同じ言語で書ける。自動検証が強い |
| **Capability-based Effects** | 効果を「能力トークン」の所有で制御 | Scala Capturing Types、Effekt系、Wyvern | ★★★★ | 効果ポリモーフィズムが自然。線形型・所有権と統合しやすい |
| **Quantitative Type Theory** | 0（消去）/1（線形）/ωを統一的に扱う | Idris 2 | ★★★★★ | 依存型＋線形型の統合に最適。証明の消去も自然 |

### 各機能のメリットと取り込み方

#### 1. Refinement Types（洗練型）
型に `{v: Int | 0 ≤ v && v < n}` のような述語を付けられます。

- **メリット**: 依存型ほど重くなく、SMTソルバ（Z3など）で多くの性質を自動証明できる。配列境界、非ゼロ除算、ソート済みデータなどを静的に保証しやすい。
- **Liquid Haskell**は実際のHaskellコードで広く使われており、totalityや関数の正しさまで検証した例がある。
- **cirka-langへの取り込み**: 線形型と組み合わせやすい。「このOwned配列の長さはnで、要素は昇順」といった性質を表現可能。自動推論を強くすると実用性が上がる。

#### 2. Effect Systems と Algebraic Effects
関数の型に「この関数はIOや例外、状態を使う」と明記する。

- **Koka**が特に参考になる。効果を型で追跡しつつ、Perceusという高度な参照カウントでGCなしに近い実行を実現している。効果ハンドラで例外・非同期・状態などをライブラリとして定義可能。
- **メリット**: 純粋関数と副作用関数を型で明確に区別できる。副作用の範囲を狭く保てる。
- **cirka-lang**: 線形なWorldや資源と組み合わせると、「この関数はファイルを開く効果を持つ」ことを型で強制できる。ハンドラはオプションで導入可能。

#### 3. Session Types
通信のプロトコル（「まずAを送り、次にBを受け取る」など）を型で表現する。

- 線形型と相性が非常に良い（チャネルの所有権を移動しながら状態を進める）。
- デッドロックフリーやプロトコル準拠を静的に保証できる。
- 分散システムやネットワークコードで特に有用。

#### 4. Contracts / 検証指向言語のアプローチ
DafnyやSPARK、Verusのように、事前条件・事後条件・不変条件を書き、SMTで自動検証する。

- 実装と仕様を同じ言語で書ける。
- VerusはRustの所有権を活かした検証ができており、cirka-langの方向性と近い。
- 証明の負担を自動化で抑えやすい。

#### 5. Capability-based Effects
効果を「能力オブジェクト」の所有で制御する方式。効果ポリモーフィズムが自然で、型注釈が軽くなりやすい。

### 優先度の提案（cirka-lang向け）

1. **最優先候補**
   - Refinement Types（Liquid風）
   - Quantitative Type Theoryの考え方（Idris 2参考）
   - 線形型との統合を前提にしたEffect/Capabilityシステム

2. **次点**
   - Session Types（通信が重要になった段階で）
   - Contracts + SMT自動検証（Dafny/Verus風の軽い証明支援）

3. **様子見**
   - フルの代数的効果ハンドラ（強力だが実装コストが高い）
   - 完全な対話的証明（Agda/Lean級）はコアには入れず、必要なら外部連携

### 現実的な導入戦略

- **段階的に**: 最初は線形型＋所有権でメモリ安全性を固め、その上にRefinement Typesを乗せる。
- **自動化を重視**: SMT（Z3など）をバックエンドに使い、ユーザーが手動証明を書く負担を減らす。
- **消去可能に**: 証明や洗練述語は実行時に消えるようにする（Quantitative Typesの0多重度が役立つ）。
- **既存資産の活用**: Liquid HaskellやVerusの設計を参考にしつつ、cirka-langの純粋性・線形型に合わせて調整する。

特に**Refinement Types**と**Effect/Capabilityシステム**は、依存型ほど重くなく、バグ削減と仕様保証にすぐ効きやすいのでおすすめです。
