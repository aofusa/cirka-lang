**cirka-lang** の標準ライブラリと数学系ライブラリの方針を提案します。

この言語の特性（純粋関数型・線形型／一意性による所有権・GCなしまたは最小・C FFIの容易さ）を活かした現実的な設計です。

### 1. 標準ライブラリの基本方針

| 層 | 内容 | 方針 |
|----|------|------|
| **core** | 言語に必須の最小限 | コンパイラと一体。純粋で線形性を意識したAPI |
| **base** | 日常的に使う基本型・関数 | 標準で同梱。ほぼ純粋 |
| **std** | 便利な標準的なライブラリ | 同梱推奨。C FFIを内部で使ってもよい |
| **外部パッケージ** | 専門的なもの | エコシステムで育てる |

**原則**:
- 純粋なAPIを優先する。
- パフォーマンスが重要な箇所は線形型で「所有権を移動して更新」できるインターフェースを用意する。
- Cの成熟したライブラリは「安全な薄いラッパー」として積極的に使う（再実装しない）。

### 2. 標準ライブラリの構成案

```
cirka-lang/
├── core/           # 言語ランタイムに近い最小限
│   ├── Prelude     # 基本関数（map, fold, 純粋なリスト操作など）
│   ├── Linear      # 線形型関連（Owned, Borrow, Dropなど）
│   ├── IO          # 線形WorldまたはモナドベースのIO
│   └── FFI         # C FFIの基本プリミティブ
├── base/           # 標準同梱
│   ├── Data/       # Maybe, Either, List, Array, Map, Set
│   ├── Control/    # モナド、Applicativeなど
│   ├── Text/       # 文字列（UTF-8中心）
│   └── System/     # ファイル、プロセスなど（線形資源として）
└── std/            # 拡張標準
    ├── Math/       # 基本数学
    ├── Numeric/    # 数値計算の入り口
    └── Foreign/    # よく使うCライブラリの安全ラッパー
```

- **リスト**は純粋・不変を基本に。
- **配列**は線形型で「所有権を持つ配列」と「借用配列」を区別し、in-place更新を可能にする。
- 文字列はRustの`String`/`&str`に近い所有権モデルを推奨。

### 3. 数学系ライブラリの扱い（重要）

数学・数値計算は「自分で全部書く」より「Cの資産を安全に使う」のが現実的です。

#### 推奨アプローチ

1. **基本数学**（`std/Math`）
   - 純粋な関数（`sin`, `cos`, `sqrt` など）はCのlibmをFFIで呼ぶ薄いラッパー。
   - ユーザーからは純粋関数に見える。

2. **線形代数・数値計算**
   - BLAS / LAPACK / OpenBLAS などをFFIでラップ。
   - インターフェースは線形型を活用：
     ```haskell
     -- 所有権を移動して破壊的更新（高速）
     gemm! :: Matrix a %1 -> Matrix a %1 -> Matrix a %1 -> Matrix a

     -- 純粋な版（内部でコピーまたは一時バッファ）
     gemm  :: Matrix a -> Matrix a -> Matrix a
     ```
   - 配列のメモリレイアウト（行優先／列優先）を明示的に制御可能にする。

3. **より高水準なもの**
   - 統計、最適化、FFTなどは外部パッケージとして育てる。
   - 初期はCライブラリ（FFTW, GSLなど）の安全ラッパーを提供。

#### パッケージ例

| パッケージ名 | 内容 | 実装方針 |
|--------------|------|----------|
| `cirka-math` | 基本数学関数 | libmのFFI |
| `cirka-linalg` | 行列・ベクトル演算 | BLAS/LAPACKの安全ラッパー |
| `cirka-numeric` | 数値積分、ODEなど | GSLなどのFFI + 純粋API |
| `cirka-array` | 高性能配列 | 線形型 + SIMDを意識 |

### 4. ブートストラップ戦略

1. **最初に用意するもの**（最小限）
   - `core` + 基本的な`base`（Maybe, List, 基本IO, FFI）
   - 文字列と配列の所有権モデル
   - C FFIの使いやすい仕組み

2. **次に優先するもの**
   - ファイルI/O、基本的なコレクション
   - `Math`の薄いラッパー
   - 簡単なテスト・ベンチマーク用の数値計算例

3. **エコシステムの育て方**
   - パッケージマネージャを早めに用意（CargoやCabalに近いもの）。
   - 「Cライブラリの安全ラッパー」を書きやすいテンプレートやツールを提供。
   - 初期はあなた（または小さなチーム）がコアと主要な数学ラッパーをメンテ。

### 5. 設計上のポイント

- **純粋性を壊さない**：C呼び出しは`IO`や線形な資源の文脈に閉じ込める。純粋関数から直接呼べないようにする。
- **ゼロコスト抽象化**：線形型の配列操作は、最終的にCのポインタ操作に近くなるよう最適化する。
- **ドキュメント**：所有権の移動がどこで起きるかを明確に書く（Rustのドキュメントに近い丁寧さ）。
- **互換性**：Haskellの基本的な型クラス（Functor, Applicative, Monadなど）はサポートし、既存の知識を活かせるようにする。
