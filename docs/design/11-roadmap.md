## 3. aCHC

順序 (ADR-027): **初期 H1–H4 (GC なし・所有権、最優先)** → CirkaLang で依存型・検証・効果を検証 → **後期 H5–H7**。

| マイルストーン | 番号 | 目的 | 着手条件 | 終了条件 |
|----------------|------|------|----------|----------|
| **H1 Haskell 最小フロントエンド** | 0100–0105 | 字句・構文・名前解決・HM 型推論・脱糖・CLI | M3 | 型クラスなしの Haskell (`fact`, `map`, 遅延リスト) が `achc run` で動く |
| **H2 Haskell 実用化** | 0110–0119 | 型クラス・cirka-base・正格性解析・IO・数値・レコード・FFI・差分テスト・初期の拡張 | H1 | 差分テスト 50 本以上が GHC と一致、リーク 0 |
| **H3 所有権拡張** | 0120–0128 | LinearTypes・LType/Unique・Drop/Release・一意配列・借用・`.chs` | H2 | 所有権エラーテスト一式。`.chs` 版ベンチを記録 |
| **H4 FFI 拡張と評価** | 0130, 0132 | `extern` ブロック、**評価レポート** | H3 | 評価レポートが CirkaLang の設計に入力されている |
| **H5 高度な型システム** | 0140–0144 | GADTs・型族・DataKinds・PolyKinds・FunctionalDependencies・型レベル Nat | H4 と **CirkaLang v0.0.4** のリリース | 各拡張の run / fail テスト |
| **H6 依存型と検証** | 0150–0154 | `foreach` とシングルトン、洗練型 (Liquid 互換 + `.chs` 構文)、契約、全域性、検査除去 | H5 と CirkaLang v0.0.4 | 検証テスト一式 |
| **H7 効果・能力・セッション型** | 0160–0164 | 能力、`Eff es a`、並行性、セッション型、後期の評価 | H5 と **CirkaLang v0.0.7** のリリース | 効果のベンチと評価レポート (FEAT-0164) |

対象外: Hackage パッケージの移植、GHC testsuite の合格率目標 (計測のみ行う)、Template Haskell、GHCi、非同期例外。

- 各版の最後のチケットが **リリースチケット** (評価・CHANGELOG・タグ `cirkalang-v0.0.N`)。
- 版の内容は評価の結果で入れ替えてよいが、版番号はリリース順に付ける。
- 開発中の版表示は `v0.0.N-dev`。

## 6. 進め方 (並行性)

```
共通:      M0 ─► M1 ─► M2 ─► M3 ─┬───────────────────────────────────────────►  SX (必要に応じて)
                                 │
aCHC:                            ├─► H1 ─► H2 ─► H3 ─► H4 (評価) ─┬─► H5 ─► H6 ──────────► H7
                                 │                                │    ▲     ▲              ▲
                                 │                                │    └─────┤              │
CirkaLang:  (0200 仕様は M0 と並行)└─► v0.0.1 ─► v0.0.2 ─► v0.0.3 ─► v0.0.4 ─► v0.0.5 ─► v0.0.6 ─► v0.0.7 ─► P2 (v0.1.0)
                                                                                         (CX: 遠隔 GUI、任意)
```

- 共通基盤 M0–M2 を最優先で進める (両試作の前提であり、GC なし・性能という最重要リスクの検証)。
- フロントエンドの前半 (aCHC 0100–0102、CirkaLang 0200–0203) は M1/M2 と並行して進めてよい (共通基盤に依存しないため)。
- **作業が競合したときの優先順位**:
  1. 共通基盤 (M0–M3)
  2. GC なし・所有権: CirkaLang v0.0.1–v0.0.3、aCHC H1–H4
  3. CirkaLang での依存型・検証・効果の検証: v0.0.4、v0.0.7 (および間の v0.0.5、v0.0.6)
  4. aCHC への取り込み: H5–H7
  5. 任意: 遠隔 GUI 検証 (CX、0052–0054)
- aCHC の後期 (H5–H7) は、対応する CirkaLang の版がリリースされるまで着手しない (ADR-027)。Hackage 移植など対象外の作業は行わない。

## 7. リスクと早期検証

| リスク | 早期検証 |
|--------|----------|
| RC のオーバーヘッドで性能が出ない | M1 の FEAT-0016 (手書き MIR vs Rust)、M2 の再利用解析、CirkaLang v0.0.1 / v0.0.3 のベンチ |
| 依存型の型検査器の工数 | v0.0.1 は依存型の機能を最小限にし (Vect 程度)、型検査器の骨格 (双方向・NbE・単一化) を先に固める |
| 二つの試作で工数が分散する | 共通基盤を最大化し、aCHC の前期のスコープを絞る (ADR-025)。後期は CirkaLang の評価後に着手 (ADR-027)。優先順位 (§6) を守る |
| 遅延評価 + RC が遅い / リークする | aCHC の H2 (正格性解析)、H3 (循環検出) で計測し、評価レポートに記録 |
| 証明が書きにくい | v0.0.4 で部分集合型の SMT 自動証明を優先し、手動証明は最後の手段にする |
| Vulkan など実用 C ライブラリの FFI が難しい | FEAT-0047 (ABI) と FEAT-0048 (bindgen) を v0.0.6 の前に完成させる。Docker では lavapipe でコンピュートのみ検証 |
| Haskell の型システムに依存型・効果を入れると複雑になりすぎる | CirkaLang で先に形を決め (ADR-027)、aCHC では GHC の流儀に合わせる。後期の評価 (FEAT-0164) で限界を記録 |
| 遠隔 GUI 検証の環境差 (ssh からの GUI 起動) | オフスクリーン描画と画像比較を基本にし、ウィンドウ起動は補助とする (15 §3.4) |
