# 12. 第二段階: CirkaLang の方向性 (草案)

第二段階では Haskell との互換性を捨て、第一段階 (aCHC) の検証結果をもとに言語を再設計する。
本書は現時点の仮説であり、P2 チケット (FEAT-0100) で第一段階の計測結果を踏まえて確定する。

## 1. 再利用するもの

aCHC のコンパイラ基盤はそのまま流用する(ADR-001/002 の主目的)。

- `cirka-diagnostics`, `cirka-core`(Core と最適化), `cirka-mir`(Perceus・検証器), `cirka-codegen-llvm`, `cirka-runtime`
- 型検査器のうち、多重度・種 `Type`/`LType`・型クラス(トレイト)の部分
- フロントエンド(構文・名前解決)は新しい構文に合わせて作り直すが、構造は流用

## 2. 変更の候補 (仮説)

| 項目 | Haskell / aCHC | CirkaLang 候補 | 判断材料 (第一段階で計測) |
|------|----------------|----------------|--------------------------|
| 評価戦略 | 遅延 | **正格がデフォルト**、`Lazy a` で明示 | サンク由来のオーバーヘッドと循環リークの頻度 |
| 所有権 | `.chs` で opt-in | 全型で所有権を推論し、`Type`/`LType` を区別 | 一意性・借用を使ったコードの書きやすさ |
| 借用 | ランク2 + `Borrow r` モナド | ライフタイム推論付きの借用構文 (`&x`, `&mut x`) | `Borrow r` の記述量 |
| 文字列 | `String = [Char]` | UTF-8 のバイト列 `Str` / `String` | 文字列処理ベンチ |
| 例外 | 純粋コードからも `error` | 純粋コードは `Result`、`panic` は回復不能エラーのみ | 例外による drop 経路の複雑さ |
| 型クラス | Haskell 型クラス | 一貫性のあるトレイト (孤児インスタンス禁止)、関連型 | |
| レコード | フィールド名がグローバル関数 | 構造体とドット記法 | |
| モジュール | Haskell モジュール | パッケージ/モジュールの明確な階層、`cirka.toml` | |
| 副作用 | `IO` モナド | `IO` を維持するか、代数的効果 (Koka 風) を検討 | 第一段階での IO + 線形資源の書き味 |
| 数値デフォルト | `Integer` | `Int` (64bit, オーバーフロー検査は debug のみ) | |

## 3. 変えないもの

- 純粋性(副作用は型で表す)
- Hindley–Milner ベースの型推論と型クラス(トレイト)
- GC を持たない(所有権 + Perceus RC + リージョン)
- LLVM によるネイティブコード生成と C FFI

## 4. 標準ライブラリ

[09-libraries.md](09-libraries.md) §2 の `cirka-core` / `cirka-alloc` / `cirka-std` の3層構成。OS とのやりとりは glibc、
基本数学は LLVM 組み込み、超越関数は libm から始めて、必要に応じて musl libm / CORE-MATH を移植する。

## 5. 移行

- aCHC で書かれた `.chs` から CirkaLang への機械的な変換ツール(構文の差分が主)を検討する。
- Haskell ライブラリとの相互運用は、aCHC でコンパイルした Haskell コードを C ABI 経由で呼ぶ形が候補。
