# aCHC 前期の評価レポート (H1–H4)

FEAT-0132。第一段階で aCHC が検証する項目 ([00-overview.md](00-overview.md) §8 の 2・3・4・7) について、前期 (H1–H4) の結果をまとめ、
CirkaLang v0.1.0 (第二段階) の設計への入力とする。

- 状態: **レビュー済み** (2026-11-06)。レビューで加えた方針を §8 に記す。
- 根拠となる計測: [bench-report.md](bench-report.md) (FEAT-0043・FEAT-0056)、[compat-report.md](compat-report.md) (FEAT-0119・FEAT-0126)、
  H3 の各チケット (FEAT-0120〜0128) のメモ。数値の再現手順はそれぞれの文書にある。
- 未着手の前期チケット: FEAT-0130 (`extern "C"` ブロック、FEAT-0047 待ち)。FFI の評価は FEAT-0116 の範囲 (`foreign import ccall`) までで行った。

## 1. 結論の要約

1. **GC なしで普通の Haskell は動く。** 互換性計測で実行できた 123 本 (GHC testsuite 104・nofib 19) はすべてリークなし。
   問題になったのは遅延評価の自己参照 (knot-tying) による循環だけで、368 本中 8 本 (2.2%)。これも試行削除の局所回収器 (ADR-043) で動く。
2. **性能は GHC -O2 に届いていない。** 素の `.hs` は GHC の 2.8〜6 倍 (FEAT-0043 の計測。FEAT-0056 の後、spectral-norm は GHC と同程度)。差の主因は GC の有無ではなく、
   サンクの生成と辞書渡しの残り (最適化器の成熟度) である。RC のコスト自体は binary-trees で Rust より速い (本ランタイムのアロケータ)。
3. **所有権拡張 (`.chs`) は、配列を線形に受け渡す書き方なら速い。** n-body の `.chs` は 1 ステップあたりの確保が 0 で GHC -O2 より速い
   (`own.chs` 6.4 s 対 GHC 7.8 s、5,000,000 ステップ)。一方で、借用 (`Borrow` モナド) を使うと当初は約 130 倍遅かった。IO の状態トークンの最適化 (BUG-0011、ADR-046) で
   約 7 倍まで縮んだが、bind を通る値の箱が残る。
   書き味も `(u, Ur x)` の受け渡しと `case` の入れ子で冗長になる。
4. **遅延評価と所有権は相性が悪い。** 一意な値がサンクに捕捉されると型だけでは RC==1 を保証できず、実行時の確認が要る (ADR-040)。
   線形専用の値を `return` できない (E0310) など、Prelude の `Type` の型変数とも衝突する。
5. **CirkaLang の方針 (正格・循環を作れない・所有権を言語の中心に置く) は、aCHC の結果から支持される。**
   捨てるもの・残すものを §5 に、CirkaLang v0.1.0 への入力を §6 に示す。

## 2. GHC 比の性能・メモリ (§8 の 2)

### 2.1 時間

`scripts/bench.sh` (Docker、3 回の平均、FEAT-0043)。比は GHC -O2 = 1。FEAT-0056 の後の値は `/usr/bin/time` の 1 回の計測 (同じ表の中でのみ比較)。

| 題材 | aCHC `.hs` | aCHC `.chs` | GHC -O2 | Rust | FEAT-0056 の後 (`.hs` / `.chs`) |
|------|------:|------:|------:|------:|------|
| binary-trees (21) | 43.9 s (2.8) | 18.4 s (1.15) | 15.9 s | 48.1 s | 変化なし |
| n-body (5M) | 25.0 s (3.2) | 6.4 s (**0.82**) | 7.8 s | 0.66 s | `.chs` は 1M ステップで 0.71 → 0.45 s |
| spectral-norm (1000) | 3.5 s (5.4) | 3.0 s (4.6) | 0.66 s | 0.20 s | `.hs` 1.79 → 0.45 s (GHC 比 約 0.7*) |
| mandelbrot (1000) | 4.7 s (5.2) | — | 0.89 s | 0.12 s | 2.64 → 2.45 s |
| fannkuch-redux (9) | 6.0 s (6.0) | — | 1.0 s | 0.033 s | 変化なし |
| array-sort (1M) | — | 2.1 s (2.9) | 0.73 s | 0.12 s | `.chs` 1.17 → 0.54 s |

\* 計測方法が異なるため参考値。次回の `scripts/bench.sh` で確定させる。

- **目標 (G3) との関係**: `.hs` が GHC -O2 と同等という目標は未達成。`.chs` が Rust の 1.5 倍以内という目標は binary-trees のみ達成。
- **差の内訳** (`CIRKA_STATS=1`):

  | プログラム | 確保 | うちサンクの評価 (forced) |
  |------|------:|------:|
  | binary-trees `.hs` (14) | 6,424,310 | 3,201,128 |
  | binary-trees `.chs` (14) | 3,223,962 | 780 |
  | n-body `.hs` (100,000) | 10,000,682 | 4,500,263 |
  | n-body `.chs` (100,000) | **806** | 304 |
  | mandelbrot `.hs` (200) | 4,035,362 | 1,961,707 |
  | fannkuch-redux `.hs` (8) | 10,294,889 | 5,913,574 |
  | spectral-norm `.chs` (300) | 5,431,296 | 272 |

  素の `.hs` では確保の約半分がサンクで、正格な書き方 (`.chs`) にするとほぼ消える。spectral-norm の `.chs` の確保は、
  `Cirka.Array.Unboxed` の要素の読み書きが `UElem` クラスのメソッドを通り、要素が箱に入ることによる (特殊化されていない)。

### 2.2 メモリ

- **リーク**: 互換性計測の 123 本、ベンチ、実行テスト全体でリーク 0 (`CIRKA_LEAK_CHECK=1`)。循環は `--cycles=collect` で回収。
- **最大 RSS**: 小さなプログラムは GHC と同程度 (計測の下限 11 MB 以下)。binary-trees は遅延評価の `.hs` (11 MB 以下) と GHC (13 MB) が
  木を実体化しないのに対し、正格な `.chs` と Rust は長寿命の木を持つので 194 MB / 258 MB。array-sort の `.chs` は要素数に比例するサンク
  (入力生成の LCG の遅延した状態) で 216 MB (GHC 103 MB、Rust 11 MB 以下)。
- **空間リーク**: fannkuch-redux の素直な `.hs` は `take`/`zip` のサンクの連鎖で 1 GB を使った (GHC でも同じ書き方なら起きうる種類のもの)。
  GC があってもなくても遅延評価の空間リークは起き、RC は「到達できるが不要なサンク」を解放できない点で GC と同じである。

## 3. 遅延評価と RC の相性 (§8 の 3)

| 観点 | 結果 | 根拠 |
|------|------|------|
| 循環の頻度 | 368 本中 8 本 (2.2%)。すべて knot-tying (`ones = 1 : ones`、ストリーム・回路の信号の再帰定義、`primes` のふるい) | compat-report §3 |
| 循環の扱い | 値の `letrec` を W0401 で警告して受理し、`--cycles=collect` で試行削除。8 本とも GHC と同じ出力・リークなし。回収しないプログラムのコストは 0 | ADR-043、FEAT-0126 |
| サンクのコスト | 素の `.hs` の確保の約半分。正格性解析・worker/wrapper・λ持ち上げ・特殊化で減るが、引数が失敗しうる遅延束縛に依存すると残る (Haskell の意味から来る制約) | §2.1、FEAT-0041/0112/0056 |
| サンクと一意性 | 一意な値をサンクが捕捉すると、評価中に参照が 2 つになる。型 (`Unique`) だけでは RC==1 を保証できず、更新の直前に実行時に RC を確かめる。サンクの評価で捕捉変数を移動して不要なコピーを除いた (修正前は in-place ソートで 10 万要素あたり 66,744 回コピー) | ADR-040、FEAT-0123 |
| 正格性の取りこぼし | タプルの成分の線形専用値が正格に評価されない (BUG-0009) など、線形専用値は常に正格という規則 (ADR-008) を遅延評価の最適化と両立させる箇所でバグが出た | BUG-0009 |
| メモリ使用量 | 遅延評価は binary-trees のように「作って捨てる」構造を実体化しないので有利な場合がある一方、空間リークの危険がある | §2.2 |

**評価**: RC (Perceus) 自体は遅延評価と矛盾しない (リーク 0、循環は 2% で局所回収器で足りる)。問題は (1) サンクの生成コストと
(2) 一意性・所有権がサンクを介した共有と衝突することである。(2) は実行時の確認で健全性は保てるが、所有権による「静的な RC==1」の
利点を弱める。CirkaLang の正格評価 (ADR-022) はこの両方を根本的に除く。

## 4. 所有権拡張の書き味 (§8 の 4)

### 4.1 うまくいったこと

- **線形に受け渡す一意な配列**: `U.read u i :: (Unique (UArray e), Ur e)` / `U.write` で書いた n-body・array-sort は in-place で、
  配列のコピー 0。n-body は 1 ステップの確保 0。
- **`.chs` と `.hs` の混在** (FEAT-0125): Haskell モードのモジュールはリークの診断だけを `warn` に緩め、安全性の検査は常にエラー (ADR-042)。
  既存コードに所有権を段階的に入れられる。
- **RAII の自動挿入** (FEAT-0122): `Drop`/`Release` の挿入は利用者に見えず、`IO` の `do` の終わりの解放も自然に書ける。
- **線形性の推論** (FEAT-0128): `swap (x, y) = (y, x)` のような注釈なしの関数が線形専用の値に使える。
- **リージョン** (FEAT-0127): 循環を含む構造をセルのアドレスで作り、まとめて解放できる。ランク 2 型で脱出を防ぐ (E0320)。

### 4.2 つらかったこと

| 問題 | 例 | 影響 | CirkaLang での対処 |
|------|----|------|------|
| 読み出しのたびの受け渡し | `case U.read u i of (u', Ur x) -> ...` を値ごとに入れ子にする (n-body の 1 組の相互作用で 8 段) | 冗長。変数名の付け替えが誤りのもと | 借用構文 (v0.0.3) で `a[i]` を共有借用の読み出しにする |
| 借用モナドのコスト | `borrowMut` + `Borrow` の `do` で同じ n-body を書くと約 130 倍遅かった (BUG-0011 の修正後も約 7 倍) | 安全で読みやすい書き方が遅い。最適化器の state hack に頼る | 借用を言語の機能にし、消去される (ライブラリのモナドにしない) (BUG-0011) |
| 入れ子の借用 | 内側の借用の中で外側の借用を使えない (リージョンの部分型がない) | 2 つの配列を同時に読む処理が書きにくい | 借用の有効範囲を構文で持つ (v0.0.3) |
| Prelude の `Type` 変数 | `return (make n)` が E0310 (`return` の `a` が `Type`)。`let` で束縛し直す必要がある | `do` の中で資源を作って返す普通の書き方が通らない | 標準ライブラリの型変数を最初から多重度・宇宙を意識して設計する |
| `Ur` での包み直し | 共有可能な結果を線形の文脈から取り出すたびに `Ur` で包む | 冗長 | 資源を持たない型は自動で複製可能とする (ADR-030 と同じ考え) |
| 多重度多相がない | `apply f x = f x` の `f` は ω の矢印になり、線形専用の値に使えない | 高階関数の再利用が制限される | QTT の多重度変数を最初から持つ (v0.0.1 済み) |
| 要素型の辞書 | `UElem` の辞書渡しが特殊化されず、要素が箱に入る | 配列の数値計算が遅い | 値型の配列を言語に入れ、要素型で単相化する |
| ワイルドカード | 線形な照合の `_` は E0302。`first (x, _) = x` は線形専用に使えない | Haskell の普通の書き方とずれる | 捨てる値は `Drop` で暗黙に解放 (CirkaLang の既定) |

### 4.3 エラーメッセージ

- E0301 (無制限な束縛)・E0302 (未消費)・E0303 (二重使用)・E0310 (`Type` 変数の具体化)・E0320 (脱出) はソース位置と修正の提案を出す。
- E0310 は原因 (`return` などライブラリの型変数) がライブラリ側にあることが多く、提案 (「`forall (a :: LType)` と宣言する」) が
  利用者には実行できない場合がある。CirkaLang では標準ライブラリの側で解決するのが筋である (§4.2)。

## 5. Haskell から捨てるべきもの・残すもの (§8 の 7)

### 5.1 捨てる (CirkaLang v0.1.0 に入れない)

| 機能 | 理由 |
|------|------|
| 既定の遅延評価 | サンクのコスト (§2.1)、一意性との衝突 (§3)、空間リーク (§2.2)。必要な所だけ `Lazy a` で明示 (ADR-022 を維持) |
| 値の自己参照 (knot-tying) | RC で回収できない唯一の原因 (§3)。正格評価では書けない設計を維持し、循環は `Lazy` と可変参照に限る |
| 局所束縛の暗黙の一般化 (`NoMonoLocalBinds`) | `where` のループが `Num a` に一般化され、辞書渡しと特殊化の失敗の原因になった (FEAT-0056)。局所束縛は単相とする |
| `MagicHash` / `UnboxedTuples` | 非ボックス値は値型として言語に入れる (compat-report §4) |
| `CPP`・`ImplicitParams`・`OverlappingInstances`・`UndecidableInstances` | compat-report §4。暗黙引数はケイパビリティ (v0.0.7) |
| `RULES` | 書き換え規則は最適化の意味を利用者に委ね、検証と相性が悪い。融合は Core の最適化で行う (FEAT-0055) |
| `unsafePerformIO`・遅延 IO | 純粋性と資源の解放時期を壊す |
| `String = [Char]` | 文字列処理のサンクとセルのコスト。バイト列ベースの文字列を標準とする (v0.0.2 の FEAT-0211) |

### 5.2 残す

| 機能 | 理由 |
|------|------|
| 代数的データ型とパターン照合 | 所有権 (移動・再利用) と相性がよい。Perceus の再利用が効く |
| 型クラス (辞書渡し + 全体プログラムでの特殊化) | 互換性計測で問題は拡張の不足だけ。辞書は特殊化で消える (ADR-032/033) |
| `do` 記法・`where`・ガード | 書き味の中心。`IO` の `do` は所有権の検査 (文を 1 回ずつ数える) とも合う |
| 純粋性と型による効果の区別 | `Drop` (純粋) と `Release` (`IO`) の分離 (ADR-006) が自然に書ける |
| 線形型 (多重度) と一意性 | 配列の in-place 更新で効果を確認。ただし言語の中心に置き、ライブラリの型変数と整合させる |

## 8. レビューで加えた方針

### 8.1 GHC -O2 と Rust を上回る性能 (ADR-047)

本レポートの結論 (§1 の 2・3) は「GHC -O2 に届かない・Rust の 1.5 倍以内を目指す」だったが、最終目標をこれより上に置く。

- **目標**: 第二段階では CirkaLang と `.chs` は Rust (release) 以上、素の `.hs` は GHC -O2 以上の速さ。G3 (Rust の 1.5 倍以内) は第一段階の通過点とする。
- **ゼロコスト抽象化**: 柔軟な型・借用・証明・トレイト・newtype などで仕様をコードとして表しても、コンパイル後の IR と機械語には影響させない。
  抽象版と手書き版が同じ機械語になることを回帰テストで確かめる。
- **最適化のヒントを中間表現に載せる**: 一意性・借用・純粋性・値域・証明など、フロントエンドが検査済みの事実を Core / MIR の注釈にし、
  LLVM の属性・メタデータ (`noalias`・`readonly`・`!range`・`!tbaa` など) まで運ぶ。誤ったヒントは未定義動作になるので、検査済みの事実からだけ作る。
- **安全性は妥協しない**: `unsafe` な高速経路を開放するのではなく、安全である証拠を最適化に使う。Rust が実行時の検査で払っている
  境界検査などのコストを、証明で消せるのが CirkaLang の優位である。
- 詳細と最適化の一覧は [16-performance.md](16-performance.md)。起票したチケット: FEAT-0058 (LLVM の属性・メタデータ)、FEAT-0059 (`UElem` の特殊化)、
  FEAT-0060 (ランタイムの LTO)、FEAT-0061 (共通部分式除去・SpecConstr・ゼロコストの回帰テスト)。既存の FEAT-0042・0051・0055・0057・0234 も同じ一覧に位置づけた。

### 8.2 ソース内のテスト (ADR-048)

Rust のように、プログラムの本体とテストを一つのソースファイルに同居させる。CirkaLang では、トップレベルの `test "名前" = 式` と、
テストのビルドにだけ存在する `tests where` ブロックで書き、`cirka test` がテストごとに別プロセスで実行する。
`cirka build` / `cirka run` は構文解析の直後にテストを捨てるので、生成コードには影響しない (ゼロコスト)。
設計は [12-cirkalang.md](12-cirkalang.md) §11、実装は FEAT-0216 (v0.0.2)。aCHC の `.hs` には入れない (Haskell の意味を変えない)。
