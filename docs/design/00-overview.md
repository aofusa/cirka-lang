# 00. 全体設計

## 1. 目的

「Haskellの型システム・純粋性を維持しつつ、トレーシングGCなしで、Rust並みの所有権・RAII・メモリ安全性と
ネイティブ性能を持つ言語」が成立するかを検証し、最終的に **CirkaLang** としてリリースする。

第一段階では、検証用コンパイラ **aCHC (aofusa's CirkaHaskellCompiler)** を作る。

## 2. TypeScript的な位置づけ

| TypeScript | aCHC |
|------------|------|
| `.js` はそのまま有効な入力 | `.hs`(Haskell 2010 + 主要GHC拡張)はそのまま有効な入力 |
| `.ts` で型注釈を追加 | `.chs` で多重度・一意性・Drop・借用・`extern` を追加 |
| `.ts` から `.js` を import できる / 逆も可 | `.chs` と `.hs` は相互に import できる |
| `tsconfig.json` の `strict` 段階 | `achc.toml` の `ownership = off / warn / strict` |
| 型を消すと JS として同じ意味 | 拡張は既存コードの意味を変えない。`.hs` の実行結果は GHC と一致させる |

**ただし実行方式は GHC と異なる。** `.hs` のコードもGCなしで実行される。共有される値は精密参照カウント
(Perceus)で、線形/一意な値は静的に解放位置が決まる。

## 3. ゴールと非ゴール(第一段階)

### ゴール

- G1. Haskell 2010 と主要なGHC拡張で書かれたプログラムを、**GCなし**でネイティブコードにコンパイルし、GHCと同じ出力を得る。
- G2. `LinearTypes` 互換の多重度に加え、**一意性型・Drop(RAII)・借用・リージョン** を型で検査する。
- G3. 拡張を使ったコードで **Rust の 1.5 倍以内** の実行時間(主要ベンチマーク)。拡張なしのコードで GHC `-O2` と同等を目標。
- G4. すべての実行テストで **リーク0**(意図的な循環を除く)と valgrind エラー0。
- G5. C関数を簡単かつ所有権付きで呼べる FFI。
- G6. (別軸・優先度低) 洗練型・契約・終了性検査・軽量依存型により、仕様を満たすこと・バグがないことを **実行時コストゼロ** で静的に確認できる([13-verification.md](13-verification.md))。

### 非ゴール(第一段階)

- GHC のコンパイル済みライブラリ(`.hi`/`.a`)とのバイナリ互換。ライブラリはソースから aCHC でコンパイルする。
- Template Haskell、GHCi、非同期例外、`-RTS` オプション、プロファイラ。
- x86_64 Linux 以外のターゲット。
- GHC の全拡張のサポート(必要に応じて段階的に追加)。
- 完全な依存型・効果システム・対話的証明(第二段階で検討。[13-verification.md](13-verification.md) §2)。

## 4. 全体アーキテクチャ(要約)

```
 .hs/.chs ──► Lexer/Layout ──► Parser ──► Renamer ──► Typechecker ──► Desugar
                                                         (型クラス・多重度・一意性・借用)
                                                                          │
                                                                          ▼
 ELF ◄── clang/lld ◄── LLVM IR ◄── MIR (所有権・RC・サンク明示) ◄── Core (System F + 多重度)
          ▲                          ▲                                   │
   libcirka_rt.a              Perceus dup/drop 挿入                Core 最適化
   (Rust, no_std)             借用推論・再利用解析                 (インライン・特殊化・正格性解析)
```

GHC のパイプライン(Parser → Renamer → Typechecker → Desugarer → Core → STG → Cmm → NCG/LLVM)を
参考にしつつ、**STG/Cmm の代わりに所有権とRC操作を明示した MIR** を置くのが最大の違い。
詳細は [01-architecture.md](01-architecture.md)。

## 5. メモリ管理の三層(要約)

| 層 | 対象 | 管理方法 | 実行時コスト |
|----|------|----------|--------------|
| 所有 (Owned) | 一意・線形な値 (`Unique a`, `%1` リソース) | 型で消費点を決め、そこで解放/再利用。`Drop`/`Release` を自動挿入(RAII) | RC操作なし |
| 共有 (Shared) | 通常のHaskell値(多重度ω) | Perceus 精密参照カウント + 借用推論 + 再利用解析 | 非アトミックRC(スレッド共有時のみアトミック) |
| リージョン (Region) | 循環・グラフ構造、一括解放したいデータ | `withRegion` スコープで確保し一括解放 | ほぼゼロ |

純粋で正格な不変データは循環を作れないため、RC だけで回収できる。循環が生じうるのは
遅延評価による knot-tying・`IORef` 等の可変参照のみで、これらは静的に警告し、リージョンや
`Weak` の利用を促す(詳細は [04-memory-model.md](04-memory-model.md))。

### 二つの軸

| 軸 | 内容 | 入力 | 優先度 |
|----|------|------|--------|
| **性能・メモリ安全** | GCなし・所有権・RAII・ネイティブ速度 | specs 00, 01, 02 | **高** (M0–M8) |
| **正しさ・仕様検証** | 洗練型・契約・終了性・依存型・ケイパビリティ・セッション型 | specs 03, 04 | 低 (M9。M5 以降に並行) |

検証の軸は性能の軸を犠牲にしない: 仕様と証明はすべて消去され、検証パスは opt-in で通常ビルドの時間も増やさない。

## 6. 主要な設計判断 (ADR)

設計を変更したらこの表に追記すること。

| ID | 判断 | 理由 | 却下した代替案 |
|----|------|------|----------------|
| ADR-001 | 実装言語は **Rust** | ランタイムとコンパイラを同一言語で書ける。第二段階の CirkaLang でそのまま再利用できる。GHCはDockerに参照実装としてのみ置く | Haskell 実装(GHC API利用): 第二段階で作り直しになる |
| ADR-002 | フロントエンドは **自作**(GHC をフォークしない) | GHC は巨大で RTS/GC と密結合。新構文(`extern`, 一意性)を入れる自由度が必要。第二段階に直結する | GHC Core プラグイン経由でCoreを取り出し独自バックエンドへ: 互換性は高いが、新構文が入れられず、GHC のバージョン追従と全 primop 実装が必要。ライブラリ互換性が最優先になった場合の「互換ブリッジ」として再検討余地あり |
| ADR-003 | 最初に **MIR + ランタイム + LLVM バックエンド** を作り、その上にHaskellフロントエンドを載せる | GCなし・ネイティブ速度という最重要リスクを先に検証できる。MIRインタプリタで正しさの基準を持てる | フロントエンドから作る: 早く動くが、メモリモデルの検証が後回しになる |
| ADR-004 | 共有値の管理は **Perceus 方式の精密RC** (Koka / Lean 4) | GCなしでHaskellの自由な共有を実現できる唯一の現実解。再利用解析で関数型のままin-place更新 (FBIP) が可能 | 全値を線形に強制: 既存Haskellが動かない。保守的RC: 解放が遅れ、リークしやすい |
| ADR-005 | 一意性は **型の種(kind)で区別**: `Type`(共有可能) ⊂ `LType`(線形専用) | Clean の一意性伝播を Haskell の型クラス/種システムに素直に載せられる。多相関数での安全性を種で保証できる | 多重度だけで表現 (Linear Haskell): 「この値は必ず一意」を表せず、CPS (`alloc :: (Array a %1 -> Ur b) %1 -> Ur b`) が必要になる |
| ADR-006 | RAII は **`Drop`(純粋・メモリのみ)と `Release`(IO内の副作用)を分離** | `drop :: a %1 -> ()` で `fclose` などの観測可能な副作用を行うと純粋性が壊れる。副作用付き解放は IO の文脈でのみ自動挿入する | 単一 `Drop`: 純粋性違反 |
| ADR-007 | 借用は **ランク2型のスコープ変数と借用モナド** (`forall r. Ref r a -> Borrow r b`) で表現 | ST モナドと同じ仕組みで、ライフタイム推論なしに脱出を防げる。純粋関数で借用を読むとクロージャ経由で脱出できるため、アクセスは `Borrow r` に閉じ込める | Rust式ライフタイム推論: 実装コスト大。第二段階で糖衣として検討 |
| ADR-008 | 評価戦略は **Haskell互換の遅延評価**。正格性解析と `Strict`/`StrictData` で削減。線形資源は常に正格 | `.hs` の意味を変えないため。資源の解放順序を決定的にするため線形値は正格 | 正格評価デフォルト: Haskell互換が崩れる(第二段階で採用候補) |
| ADR-009 | バックエンドは **LLVM IR をテキストで生成** し `clang` でコンパイル・リンク | LLVM の Rust バインディングのバージョン追従が不要。生成物が読めてデバッグしやすい。C ABI と完全一致 | inkwell(LLVM C API): 将来コンパイル速度が問題になれば移行。Cranelift: 最適化性能が劣る |
| ADR-010 | 第一段階は **全体プログラムコンパイル** (MLton 方式) | 型クラスの特殊化・単相化で Rust 並みの性能を出しやすい。分離コンパイル用インタフェースはキャッシュとして後から追加 | 分離コンパイル: 最適化機会が減る |
| ADR-011 | 末尾呼び出しは LLVM の `tailcc` + `musttail` で保証 | Haskell の相互再帰ループに必須 | トランポリン: 遅い |
| ADR-012 | `base` は **aCHC 用に再実装** (`lib/cirka-base`)。GHC の base(BSD-3)から移植可能な部分は移植 | GHC の base は GHC 固有 primop・RTS に強く依存しており、そのままでは使えない | GHC base をそのまま: 全 primop の再現が必要 |
| ADR-013 | 例外は最初は **abort**(stdoutをフラッシュして終了)、後に **Itanium ABI のアンワインド + landing pad で drop** | Rust の panic=unwind と同じ実績ある方式。初期実装を単純に保つ | 戻り値でのエラー伝播: 全呼び出しにチェックが入り遅い |
| ADR-014 | 循環参照は **リーク扱い(安全)+ コンパイル時警告**。オプションでローカルな循環回収器 | Rust の `Rc` と同じ立場。トレーシングGCを持たない原則を守る | 常時循環回収器: GCを持つことになる |
| ADR-015 | 検証機能は **実行時コストゼロ・opt-in** の独立した軸とし、性能の軸より優先度を下げる | 性能目標を犠牲にしない。注釈のないコードに影響しない | 型検査に常時組み込み: ビルドが遅くなる |
| ADR-016 | 第一段階の中心は **洗練型 (Liquid Haskell 互換) + 契約**。Core 上の独立パスで VC を生成し **Z3** で検証 | Haskell の型推論を変えずに載せられることが Liquid Haskell で実証済み。`{-@ @-}` 注釈は `.hs` でも書ける (TS の checkJs に相当) | 第一段階で完全な依存型: Haskell の型推論・型クラスと衝突し、フロントエンドの作り直しになる |
| ADR-017 | 第一段階の依存型は **GHC 相当の軽量版** (DataKinds/GADTs/型族/型レベル Nat ソルバ)。完全な依存型は第二段階で **QTT** に基づき Core から作る | 多重度 0/1/ω は既に QTT の半環そのもので、Core を自然に拡張できる | Dependent Haskell 方式: GHC でも未完成 |
| ADR-018 | 効果システム (Koka 風) は **第二段階**。第一段階はケイパビリティをライブラリで提供 | 関数型の形を変えるため Haskell 互換と両立しない | 第一段階で導入: `.hs` との互換性が壊れる |
| ADR-019 | 証明できた事実で **実行時検査を除去** する (境界検査・ゼロ除算・到達不能分岐) | 検証機能を性能向上にもつなげる | 検証結果をコード生成に使わない: 機会損失 |

## 7. 段階と検証項目

第一段階で検証し、第二段階の設計判断に使う項目:

1. Perceus RC のみで、既存 Haskell プログラムの性能・メモリ使用量はどうなるか(GHC 比)。
2. 遅延評価と RC の相性(サンクのオーバーヘッド、knot-tying の頻度)。
3. 一意性・線形性・借用を使ったコードの書きやすさ、エラーメッセージの分かりやすさ。
4. Rust と比べた性能差の主因。
5. Haskell の何を捨てれば言語がシンプルになるか(→ [12-cirkalang.md](12-cirkalang.md))。

計測結果は各チケットと `docs/design/` に記録する。
